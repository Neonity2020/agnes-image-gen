第 9 章：浏览器持久化与数据迁移

目标：关闭或刷新页面后仍能恢复会话；面对空间不足、损坏 JSON 和旧版数据时，应用保持可用而不是崩溃。

1. localStorage 是便利的本地数据库，不是可信数据源

浏览器可以被用户修改、旧版本可以留下不同结构、写入还可能因配额失败。因此不要直接把 JSON.parse(...) 的结果断言成 Conversation[]。正确顺序是：读取字符串、try/catch 解析、检查顶层类型、逐条规范化、丢弃无效值、限制数量。

export function readConversations(): Conversation[] {
  try {
    const value: unknown = JSON.parse(localStorage.getItem(CONVERSATIONS_STORAGE) ?? "null")
    if (Array.isArray(value)) {
      return value.map(normalizeConversation)
        .filter((item): item is Conversation => item !== null)
        .sort((a, b) => b.updated - a.updated)
        .slice(0, MAX_CONVERSATIONS)
    }
  } catch { /* fall through */ }
  return legacyConversations()
}

2. 用运行时校验修复 TypeScript 的盲区

TypeScript 类型只在编译时存在；localStorage 返回的是未知 JSON。规范化函数至少检查会话 ID、标题、时间戳、entries 数组，并对每个 entry 调用类型守卫：

function normalizeConversation(value: unknown): Conversation | null {
  if (!value || typeof value !== "object") return null
  const item = value as Partial<Conversation>
  if (typeof item.id !== "string" || typeof item.title !== "string" ||
      typeof item.created !== "number" || typeof item.updated !== "number" ||
      !Array.isArray(item.entries)) return null
  return { ...item, entries: item.entries.filter(isConversationEntry).slice(-MAX_ENTRIES_PER_CONVERSATION) } as Conversation
}

生产代码可避免最后的断言，逐字段重新构造对象。重点是不要信任持久化的嵌套数组。

3. 限制数据，才能有可预测的体验

本项目最多保留 30 条会话、每条会话最多 50 条 entry。写入前再次应用限制并按 updated 倒序，以确保“最近对话”与实际存储一致：

const value = conversations
  .map((conversation) => ({ ...conversation,
    entries: conversation.entries.slice(-MAX_ENTRIES_PER_CONVERSATION) }))
  .sort((a, b) => b.updated - a.updated)
  .slice(0, MAX_CONVERSATIONS)
localStorage.setItem(CONVERSATIONS_STORAGE, JSON.stringify(value))

图像 Data URL 很大，特别容易触发配额。写入应包在 try/catch 中：内存里的本轮对话仍可继续，UI 用 Toast 提醒用户本地记忆未保存。

4. 迁移要读取旧格式，而不是删除旧用户数据

从“一个活动文本数组 + 扁平生成历史”迁到 Conversation[] 时，读取函数先检测新版 key。不存在时：

  1. 将旧活动文本条目合成一个 legacy 会话。
  2. 将未包含在活动会话中的旧历史记录分别转成单条会话。
  3. 以更新时间排序、去除重复 ID，并应用同样的上限。

之后任一次新的会话状态写入都会落到新版 key。迁移只需发生在读取边界，React 组件从始至终只看到新版 Conversation[]。

不要在渲染组件中写 migration。迁移是存储格式适配，应该集中在 src/lib/storage.ts；这样更容易删除旧支持，也便于单独测试。

5. API Key 的现实边界

API Key 也保存在 localStorage，方便同一设备复用，但它并不“安全保存”：任何能在该站点执行的脚本都有读取可能。教程应明确告知读者：这是个人原型的便利设计；面向多人生产环境时应使用服务端、受限 token 或 OAuth。

动手练习

  1. 在 DevTools Application 面板手动写入无效 JSON，刷新后确认应用显示空状态而非白屏。
  2. 写入一个缺少 updated 的对象，确认规范化函数丢弃它。
  3. 创建超过上限的假会话，验证只保留更新时间最新的一批。
  4. 模拟 localStorage.setItem 抛错，确认本轮 UI 仍可看到生成结果。
  5. 准备旧格式 key，验证首次加载能看到转换后的线程。

自检：若某段读取代码使用 JSON.parse(...) as Conversation[]，它只是在隐藏坏数据；应改为运行时校验。

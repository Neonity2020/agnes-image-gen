第 1 章：认识目标应用与技术架构

目标：在写第一行业务代码前，能清楚说明一次用户创作请求如何穿过界面、Agent、模型 API 与浏览器存储。

1. 先看应用要解决什么

这是一个纯浏览器端创作工作台。读者输入提示词，选择文本、图片或视频模式；应用调用 Agnes 并把结果放进当前对话。它还支持图生图、历史线程与本地恢复。

“纯浏览器端”是本教程的一个刻意选择：没有自己的业务服务器。浏览器直接请求 Agnes API，因此界面响应快、部署简单，但 任何以 VITE_ 开头的配置和用户输入的 API Key 都处在客户端信任边界内。不要把它误解为服务端秘密管理方案。

2. 一次请求的完整路径

用户提交提示词 │ ▼ PromptComposer 提交表单 │ ▼ App.handleSubmit ├─ 创建 loading ConversationEntry ├─ 从当前线程提取最近文本问答作为 history └─ 调用 runAgnesAgent │ ▼ LangGraph route ├─ text → generateText ├─ image → generateImage └─ video → generateVideo │ ▼ Agnes API │ ▼ 回写同一 conversationId + entry id │ ▼ Conversation 渲染 + localStorage 持久化

这条路径的核心不是“组件之间互相调用”，而是每层只做一种转换：UI 收集意图，App 管理用户可见状态，Agent 选择能力，API 模块负责网络协议，存储模块负责恢复。

3. 识别四个关键模块

  • src/main.tsx 是最小入口：将 App 挂载到页面。
  • src/App.tsx 是协调者：维护当前会话、输入模式、并发数量及异步结果回写。
  • src/lib/agent.ts 是路由器：LangGraph 根据 mode 选择 write、draw 或 animate 节点。
  • src/lib/agnes.ts 是协议适配器：它知道请求 URL、请求体、超时、视频轮询和模型返回格式；其他模块不应该知道这些细节。

这是一条很实用的复刻原则：让变化最快的外部协议被隔离在一个模块里。将来更换模型供应商时，优先修改 agnes.ts，而不是把判断散落到组件中。

4. 会话状态为何放在 App

Conversation 包含标题、创建/更新时间以及一组 ConversationEntry。App 只渲染活动会话的条目，并在提交时给每个请求同时分配会话 ID 和条目 ID。这样即使用户在生成期间切换到另一条线程，返回结果也能被写回原线程。

多轮上下文只来自当前线程中成功的文本问答；图片和视频结果可以保留在会话显示中，却不应被拼进文本模型的 messages 数组。

5. 动手：在仓库里画出你的架构图

  1. 打开 src/App.tsx，找到 handleSubmit。
  2. 标出它读哪些状态、写哪些状态，以及唯一的异步边界 runAgnesAgent。
  3. 打开 src/lib/agent.ts，写下三种 mode 分别会到达的函数。
  4. 打开 src/lib/storage.ts，回答：刷新页面后哪个数据能恢复，哪个运行时数据不能恢复？

自检：你应能用一句话回答：“视频为什么需要在 API 模块轮询，而不由 React 组件直接轮询？”答案是：网络协议和轮询策略属于外部服务适配细节，应集中在 agnes.ts。
